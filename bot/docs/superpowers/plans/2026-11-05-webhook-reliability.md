# Проверка и исправление надёжности webhook

> Для исполнения: `superpowers:executing-plans`; работа по задачам с циклом
> «воспроизвести ошибку → исправить → проверить», затем независимый обзор.

**Цель:** устранить воспроизводимые ошибки при получении событий MAX и дать
оператору проверку всей локальной цепочки HTTPS → Nginx → бот.

**Архитектура:** сохраняются один процесс бота, webhook, последовательность
диалога пользователя, существующая БД и Nginx в Compose. SDK и управление
подпиской используют общий HTTP-клиент с настоящей отменой зависших запросов.
Изменения GLPI не откатываются автоматически.

**Технологии:** Node.js 22, SDK MAX 0.2.5, Axios, node:test, Docker Compose v2,
Nginx 1.28, тестовые HTTP/TLS-серверы.

## Ограничения

- Не читать `.env`, секреты и прототип `miniproject`; не выводить токены.
- Не вызывать боевые MAX/GLPI из облачных тестов.
- MAX `/updates` и запуск polling остаются запрещёнными.
- Сохранять тексты бота и существующие сценарии GLPI.
- Не считать успешные HEAD, readiness или регистрацию подписки доказательством
  доставки настоящего события MAX.

## Что установлено до исправлений

Исходная версия: `89e67a2`, ветка `feat/glpi-max-webhook`.

1. SDK вызывает `fetch` без таймаута. При удержании ответа `/messages` первый
   webhook и следующие сообщения этого пользователя ждут; `/health` даёт 200.
   `server.requestTimeout` ограничивает приём тела, а не исполнение хендлера.
2. Сохранение темы/описания заявки до `ctx.reply` позволяет повтору после 500
   принять тот же текст за следующий ответ пользователя.
3. `bot_started` не дедуплицируется: повтор сбрасывает уже продолженный диалог.
4. SDK допускает callback без исходного сообщения, но его `ctx.reply` требует
   `chat_id`; без него личный ответ не отправляется.

Это подтверждённые локальные дефекты. Они не доказывают причину отсутствия
реальных POST в последних предоставленных журналах сервера.

## Задачи

- [x] Общий клиент `transport/maxClient.js`: таймаут 30000 мс, AbortSignal,
  отсутствие автоматического повтора POST/redirect, запрет `/updates` на уровне
  всех SDK-вызовов. Подключить через публичный `Api(client)`, не менять global fetch.
  Тест: реальный сервер удерживает заголовки/тело ответа, запрос отменяется,
  очередь пользователя освобождается, другое событие проходит.
- [x] Исправить два перехода текста в `ticketController.js`: не мутировать
  исходную сессию и фиксировать переход после успешной отправки подсказки.
  Тест: 500 и повтор того же mid не продвигают заявку дважды.
- [x] Создавать один SDK Context для события; callback без message получает
  личный ответ по user_id. Дедуплицировать одинаковые bot_started по
  timestamp/chat/user/payload. Тесты настоящих контроллеров и SDK.
- [x] Добавить внутреннюю диагностику приёма, отказов, обработки и активных
  запросов; фиксировать вход до проверки секрета. Подготовить
  `scripts/diagnose-webhook.mjs`: выбранные поля подписки, локальный POST и POST
  через Docker Nginx с проверкой TLS, наблюдение входящих событий.
- [x] Прогнать регрессионные тесты и настоящий Docker smoke, включая исходящие
  SDK-вызовы, восстановление после таймаута и смены IP бота. Записать выводы и
  пределы доказательств в `WEBHOOK_AUDIT.md`, пройти независимый обзор, commit/push.

## Проверка перед завершением

`DOTENV_CONFIG_PATH=/dev/null node --experimental-vm-modules --test test/*.test.js`
и `bash test/docker-nginx.smoke.sh` на Node.js 22.

Вне облачных тестов остаётся сквозная проверка конкретного рабочего аккаунта
MAX и реальных GLPI/SQL/SMTP. Повтор `attachment.not.ready` ограничен тремя
попытками. Долговечная идемпотентность GLPI остаётся отдельной задачей;
таймаут HTTP не равен отмене уже совершённой операции удалённого сервиса.

Результат проверки: 62 теста, 61 успешен, один MariaDB пропущен, ошибок нет.
Docker smoke с настоящим SDK HTTP и TLS прошёл. Независимый обзор принят после
исправления ложного успеха диагностики другого upstream (nonce + ID процесса).
