# Сравнение трёх MAX-ботов и порядок дальнейшей работы

5 ноября 2026. База GLPI — `c7b5515`, ЖКХ — `0bf68ba`, бот обращений —
локальная копия архива `123.zip`. Совпадение этих исходников с рабочими образами
этим анализом не установлено. `.env`, токены и приватные ключи не читались.

## Что доказано последними счётчиками

`received=3`, `message_created=1`, `failed=0`, `active=0` подтверждают одно
распознанное событие и отсутствие незавершённых запросов в момент снимка.
Остальные запросы могут быть диагностическими пробами. Это не подтверждает
отправку ответа и не описывает `/start`, отправленные после снимка.

Тип события подсчитывается до middleware. `processed` означает завершение
middleware, включая ранний `return`, а не отправленное сообщение. Дубликат
получает HTTP 200 без нового ответа. Источники: `transport/maxTransport.js`,
`transport/updateDispatcher.js`, `controllers/messageController.js:30` и `:35`.

Дополнительное наблюдение пользователя: в период молчания другие пользователи
тоже не получают ответ. Одна очередь dialog.wait не объясняет общий отказ;
приоритет проверки — общий приём событий, зависимости и исходящий MAX API.

Выводы из сравнения:

1. Все три реализации ждут обработчик. Объяснение «Python немедленно отдаёт 200,
   поэтому работает» не подтверждается исходниками.
2. GLPI сильнее зависит от внешних баз уже на входе. Дальнейший импорт может ждать
   130 секунд плюс проверки (`config/env.js:49`, `services/sdsService.js:87`).
   Таймаут зависимости не ограничивает весь handler. Бюджет ожидания MAX надо
   подтвердить документацией или измерением; конкретное число здесь не установлено.
3. Входящие события одного пользователя GLPI обрабатывает последовательно.
   Медленный handler удерживает следующие (`dialog.wait`). Фоновые обработчики
   СДС обходят эту очередь и меняют ту же сессию (`controllers/sdsController.js:114`,
   `:145`). Это риск гонки состояния; его связь с текущим молчанием не доказана.
4. ЖКХ тоже не эталон изоляции: синхронный SQL вызывается из async-обработчиков.
   Сам перенос языка или копирование запуска Python-бота устойчивость не докажут.
5. Webhook доставляет входящие события. Ответы/уведомления остаются POST /messages.
   Опрос GLPI не получает события MAX. В GLPI /updates запрещён до сетевого запроса.
6. Есть синхронное чтение всего вложения для определения сигнатуры
   (`services/glpiService.js:58`) и синхронные exists/stat (`:576`, `:580`).
   При медленном диске они задерживают event loop всех пользователей. Следующая
   отдельная оптимизация — async stat/open и чтение только нужного префикса.
   Наличие этих вызовов не доказывает зависание в текущем эпизоде.

## Воспроизведённый дефект и текущая правка

SDK извлекает message из HTTP 200 без проверки результата:
`node_modules/@maxhub/max-bot-api/dist/api.js:30`,
`dist/core/network/api/base-api.js:10`. JSON без message возвращал undefined из
ctx.reply; событие завершалось успешно и попадало в completed-дедупликацию.
CheckedBot из архива отдельно проверяет отсутствие результата.

Теперь отправка требует message.body.mid. Иначе возникает безопасная ошибка
MAX_API_UNCONFIRMED, тело ответа не выводится, событие не попадает в completed.
Автоматического повтора неопределённой отправки внутри клиента нет. MAX мог
принять сообщение до испорченного ответа: повтор webhook всё равно может дать
дубликат. Это не exactly-once доставка и не установленная причина живого сбоя.

Новые метрики attempted/confirmed/failed связаны с входящим событием через
AsyncLocalStorage. Хранятся последние 20 завершённых реальных событий; пробы их
не вытесняют. Новые логи не содержат текст, адресата, mid, payload или секрет.
Метрики относятся к новым сообщениям внутри webhook; фоновые уведомления,
editMessage и answerOnCallback сюда не входят. Подтверждение API не доказывает
отображение или прочтение сообщения клиентом MAX.

Регрессия: `test/webhook-reliability.test.js` — неподтверждённый HTTP 200 → ошибка,
повтор события → успех, следующий повтор → дедупликация; параллельные диалоги
не смешивают подтверждения; история ограничена и не засоряется пробами.

## Где наш процесс был слабым

- Мы исправляли настоящие локальные дефекты, не подтверждая их связь с каждым
  рабочим эпизодом. Исправления и ограничения есть в [WEBHOOK_AUDIT.md](WEBHOOK_AUDIT.md).
  Регрессия проверяет конкретный сценарий, а не живую связку MAX/GLPI/SMTP.
- Подписка, health и локальные POST не проверяли отправку пользовательского ответа.
  Теперь она видна отдельно. Access log появляется после завершения запроса.
- Перенос Nginx в Docker менял сетевую схему одновременно с расследованием кода.
  Обе схемы допустимы; HEAD 403 задан конфигурацией и не проверяет работу handler.
- Результат «Последний фикс старта: false» показывал несовпадение Git и рабочего
  контейнера. Проверка релиза должна включать фактический образ и instance_id.
- Два снимка за 30 секунд могут пропустить краткий сбой и не описывают последующее
  молчание. Данные нужны после неудачного сообщения, до ручного рестарта.

## Дальнейший порядок работы

1. Одна гипотеза → воспроизводящий тест → одна поставка. Записывать Git SHA,
   ID образа, instance_id, время и ожидаемое изменение. Сохранять образ для отката,
   не пересоздавать БД и её тома. Локальное сравнение не требует доступа к секретам.
2. После обновления проверить в живом MAX: /start, кнопку, текст, ещё один /start
   после паузы. Сопоставить диагностику до/после молчания с логами Nginx и Node.
   Сейчас команда показывает историю пяти событий; --watch 0 собирает уже
   накопленные результаты без нового окна. Локальные пробы не заменяют сценарий.
3. При подтверждённых долгих handler следующий архитектурный этап — durable inbox
   в MariaDB: сначала commit события, затем HTTP 200, затем worker по пользователю.
   Нужны leases, восстановление после рестарта, ограниченные повторы и метрики очереди.
   Просто res.end(200) + фоновый Promise теряет событие при остановке процесса.
4. Отдельно проектировать идемпотентность GLPI и outbox: таймаут POST /Ticket не
   означает отсутствие созданной заявки. До этого не выносить poller произвольно
   в другой процесс: сессии кэшируются в памяти, нужен общий порядок их изменений.

| После нового неудачного сообщения | Что проверять |
| --- | --- |
| Типы событий не растут, instance_id прежний | received/rejected/failed, active/http.body, Nginx; запуск handler ещё не подтверждён |
| active с dialog.wait | Предыдущее событие того же пользователя и его зависимость |
| active с db.*, glpi.*, max.api/max.send | Конкретную зависимость и длительность |
| Событие завершено, replies=0 | duplicate, ранний return, маршрут или действие без нового сообщения; это не автоматически дефект |
| replies.failed растёт | Ошибку отправки, в том числе перехваченную handler; webhook может дать 200 после нейтрального ответа |
| replies.confirmed растёт | MAX подтвердил создание сообщения; проверять адресата/учётную запись и результат в мессенджере |
