Проверены миграция `7c30102..89e67a2`, SDK MAX 0.2.5, HTTP-транспорт,
контроллеры, повторы и Nginx. Рабочие `.env`, токены, приватные ключи и

| Callback без исходного message | ctx.reply падает без chat_id | Личный ответ по user_id: `webhook-reliability.test.js`, null и отсутствующее поле |

Все эти ошибки воспроизведены до исправлений и проверены после. Это доказанные
дефекты кода, но причина последнего эпизода на рабочем сервере ещё не установлена.

`server.requestTimeout` ограничивает получение запроса, а не контроллер.
SDK и подписка теперь используют общий `maxClient.js`: TLS/proxy, таймаут
JSON-запроса 30000 мс с AbortSignal, запрет redirect и безопасные ошибки без
Axios config. `/updates` запрещён на нижнем уровне, включая raw/кодированный путь.
Обычные сетевые ошибки POST не повторяются автоматически; два повтора относятся
только к явному отказу attachment.not.ready.

## Чего не хватало в нашей предыдущей работе

- `/me` и `/subscriptions` проверяли Axios; ответы SDK шли через другой клиент,
  fetch без ограничения времени. Его зависание исходные тесты не проверяли.
- Прежний Docker smoke подменял sendMessageToChat функцией. Теперь он использует
  настоящий SDK HTTP, локальный MAX-сервер и намеренно зависший ответ.
- Readiness подтверждает запуск, а не завершение диалога или доставку ответа.
- HEAD 403 задан правилом Nginx «только POST». `--resolve` обходит DNS, а VPN
  меняет путь проверки; это не проверка маршрута отправителя MAX.
- Access log Nginx пишется после завершения запроса. Отсутствие строки за короткое
  окно не доказывает отсутствие открытого соединения/незавершённого POST.

Nginx на хосте — допустимая схема. Docker меняет путь файрвола и общую сеть,
но сам по себе не исправляет обработчики MAX.

## Одна проверка на сервере после обновления образа

```bash
sudo docker exec -i max_bot node scripts/diagnose-webhook.mjs --watch 30
```

Команда проверяет выбранные поля учётной записи/подписки, POST в Node и POST
через nginx:443. HTTPS проверяет цепочку и имя сертификата с правильным SNI.
Каждая проба сверяется по случайному nonce и ID текущего процесса. HTTP 200
другого upstream не считается успехом — это проверено отдельным TLS-тестом.

Тип diagnostic_probe игнорируется: бизнес-хендлеры, сессии, GLPI и отправка
сообщений MAX не вызываются; подписка не меняется, секреты не печатаются.
Затем оператор отправляет /start во время окна 30 с. Три типа событий MAX
подсчитываются отдельно от проб. Внутренний `/diagnostics` показывает POST,
отказы, ошибки, активные запросы и их возраст; Nginx этот путь не публикует.
Лог request появляется до проверки секрета/тела, rejected объясняет отказ.
Текст, MAX ID и секрет в эти записи не включаются.

## Пределы доказательств

- HTTP/TLS и Docker подтверждают локальные ошибки и исправления. Реальные
  MAX/GLPI/SQL/SMTP проверяются на рабочем сервере отдельно.
- Успех локальных проб при отсутствии события MAX не устанавливает виновника
  внешней недоставки. Для неё ещё нужны данные DNS/NAT/файрвола и провайдера.
- MAX-ответ и SQL-сессия не являются одной транзакцией. Полный outbox и
  долговечная идемпотентность GLPI между рестартами не добавлялись; автоматически
  откатывать уже созданные заявки/комментарии нельзя.
- Таймаут не доказывает, что удалённая сторона не выполнила POST.
- Зависший SQL или другая зависимость будут видны по активным запросам;
  новый таймаут относится к MAX API, сериализация диалогов сохраняется.
