# Webhook GLPI-бота MAX

Для текущей версии с таблицей событий и RabbitMQ используйте
[RABBITMQ_DEPLOY.md](RABBITMQ_DEPLOY.md). Ниже сохранены прежние инструкции
для синхронного Node и Nginx; обновлять только max_bot после миграции нельзя.

Публичный URL берётся из WEBHOOK_URL. В актуальных логах сервера домен
**bot-support.gov70.ru** (с дефисом); прежний **botsupport.gov70.ru** остаётся
в примерах. При настройке сверяйте домен в подписке MAX, Nginx и WEBHOOK_URL.

## POST /max/callback получает 301, затем GET получает 403

Prefix location `/max/callback/` в Nginx может автоматически отправлять 301
для `/max/callback`. При следовании такому редиректу клиент может заменить
POST на GET и потерять JSON события. В логах это видно как POST301 без upstream,
затем GET403; счётчик message_callback в Node при этом не растёт.

Исправление — внутренний переход к тому же обработчику, без HTTP-редиректа:

```nginx
location = /max/callback {
    rewrite ^ /max/callback/ last;
}
```

Существующий location `/max/callback/` с proxy_pass сохраняется. Оба шаблона
Nginx содержат этот маршрут; Node тоже принимает один необязательный конечный
slash. POST-only и проверка X-Max-Bot-Api-Secret действуют в обоих вариантах.

Быстро применить к действующему bind-конфигу, сохранив местные правки домена,
сертификатов и не меняя checkout репозитория:

```bash
(
set -euo pipefail
cd /opt/max-bot/rcair-pgli
git fetch origin feat/glpi-max-webhook
GLPI_FIX_SCRIPT="$(mktemp /tmp/glpi-callback-fix.XXXXXX)"
trap 'rm -f "$GLPI_FIX_SCRIPT"' EXIT
git show FETCH_HEAD:bot/deploy/fix-callback-path.sh > "$GLPI_FIX_SCRIPT"
sudo bash "$GLPI_FIX_SCRIPT"
)
```

Helper находит именно файл, подключённый к /etc/nginx/conf.d/default.conf в
max_bot_nginx, создаёт уникальную backup, записывает правку в тот же inode,
проверяет nginx -t и делает reload. При неудачной проверке возвращает исходный
файл. Бот и БД продолжают работать; изменения подписки MAX не требуются.
Произвольный уже существующий bare location helper не перезаписывает. Если
bind-файл на хосте отличается от файла в контейнере, останавливается до правки:
сначала нужно разобраться, какой конфиг фактически подключён.

После применения отправьте /start и нажмите «Справка» на новом меню. Ожидаются
POST200/upstream=200 без промежуточного 301 и новое событие message_callback.

```text
MAX → botsupport.gov70.ru:443 → Nginx (TLS) → Node.js:3000 → существующие обработчики → GLPI
```

Для текущего сервера `10.230.101.48` Nginx и бот запускаются отдельными
контейнерами одного Compose-проекта `max-bot`. Nginx обращается к
`max-bot:3000` через Docker-сеть; публичный порт — 443. Внешний адрес домена —
`91.210.184.36`, проброс должен вести на `10.230.101.48:443`.

## Перенос существующего Nginx в Docker

Предполагается уже работающий webhook-бот: контейнер `max_bot` имеет статус
`healthy`, а `http://127.0.0.1:3000/health` доступен на хосте. Существующие файлы
`/opt/max-bot/docker-compose.yml`, `/opt/max-bot/docker-compose.webhook.yml`
и `/opt/max-bot/webhook.env` сохраняются. Образ бота, MariaDB, её тома,
настройки интеграций и загрузки не меняются этим переключением.

Сертификат и ключ остаются на сервере в
`/etc/nginx/tls/botsupport.gov70.ru/{fullchain,privkey}.pem` и подключаются
в контейнер только для чтения. Приватный ключ не копируется в репозиторий или образ.

На сервере:

```bash
cd /opt/max-bot/rcair-pgli
git pull --ff-only origin feat/glpi-max-webhook
sudo bash bot/deploy/use-docker-nginx.sh
```

Скрипт добавляет [deploy/docker-compose.nginx.yml](deploy/docker-compose.nginx.yml)
последним Compose-файлом в проект `max-bot`. Сначала скачивает Nginx и проверяет
TLS-конфигурацию временным контейнером без публикации портов. Затем останавливает
Nginx на хосте и запускает только сервис `nginx` с `--no-deps`: бот и БД
не перезапускаются. После healthcheck и проверки локального HTTPS отключает
автозапуск хостового Nginx, чтобы избежать конфликта за 80/443 после перезагрузки.
Если переключение не удалось, скрипт останавливает Docker Nginx и возвращает хостовый.

```bash
sudo bash bot/deploy/use-docker-nginx.sh status
sudo docker logs --since 5m --tail 50 max_bot_nginx
sudo docker logs --since 5m --tail 80 max_bot
```

Отправьте `/start` в MAX. В журнале Nginx нужен новый POST с
`200 upstream=200`, в журнале бота — `[MAX_WEBHOOK]`, в чате — ответ.
Локальный GET/HEAD к callback получает `403` по правилу «только POST».
Проверка здоровья Nginx выполняется через внутренний `127.0.0.1:8081/health`
с проксированием к боту; этот порт не публикуется. Docker DNS повторно определяет
адрес бота, поэтому его пересоздание не требует перезапуска Nginx.

Откат к прежнему Nginx на хосте:

```bash
sudo bash /opt/max-bot/rcair-pgli/bot/deploy/use-docker-nginx.sh rollback
```

Не запускайте параллельно хостовый и контейнерный Nginx на одних портах.
Loopback-публикация бота `127.0.0.1:3000:3000` сохраняется для диагностики
и отката. При последующих обновлениях Compose используйте все три файла;
`docker compose down` для этого переноса не нужен. Контейнер `nginx` имеет
`restart: unless-stopped`, поэтому поднимается после перезагрузки Docker.

Перенос меняет путь обработки пакетов файрволом: опубликованный Docker-порт
обычно использует цепочки Docker/FORWARD вместо INPUT хоста. Правила
DOCKER-USER/FORWARD, внешний NAT и DNS всё равно должны пропускать трафик.
Контейнеризация сама по себе не доказывает внешнюю доступность. Продление
скопированного сертификата нужно отдельно доставлять в этот каталог с reload Nginx.

Для воспроизведения проверки без рабочих секретов и `.env`:

```bash
cd bot
npm ci --ignore-scripts
bash test/docker-nginx.smoke.sh
```

Нужны Docker Compose v2, OpenSSL, curl и rg. Тест создаёт отдельный проект,
временный сертификат и локальную заглушку MAX; проверяет TLS с проверкой имени,
секрет, `/start` через настоящий SDK и исходящий HTTP, дедупликацию, HTTP 500,
отмену зависшего запроса и восстановление после смены IP контейнера бота.
Свои контейнеры и сертификат тест удаляет.

## Обновление образа после исправлений

`git pull` обновляет исходники. Запущенному контейнеру нужен новый образ.
От обычного пользователя:

```bash
cd /opt/max-bot/rcair-pgli
git switch feat/glpi-max-webhook
git pull --ff-only origin feat/glpi-max-webhook
```

Сборка и обновление только бота, с резервным тегом прежнего образа:

```bash
sudo bash <<'BASH'
set -euo pipefail
cd /opt/max-bot
args=(-p max-bot)
if [ -f /opt/max-bot/.env ]; then args+=(--env-file /opt/max-bot/.env); fi
args+=(
  --env-file /opt/max-bot/webhook.env
  -f /opt/max-bot/docker-compose.yml
  -f /opt/max-bot/docker-compose.webhook.yml
  -f /opt/max-bot/rcair-pgli/bot/deploy/docker-compose.nginx.yml
)
docker compose "${args[@]}" config --quiet
previous_image="$(docker inspect -f '{{.Image}}' max_bot)"
backup_tag="max-glpi-bot:before-audit-$(TZ=Asia/Tomsk date +%Y%m%d-%H%M%S)"
docker image tag "$previous_image" "$backup_tag"
echo "Резервный образ: $backup_tag"
docker compose "${args[@]}" build max-bot
if ! docker compose "${args[@]}" up -d --no-deps --no-build --wait --wait-timeout 120 max-bot; then
  echo 'Возвращаем прежний образ бота.' >&2
  docker image tag "$previous_image" max-glpi-bot:webhook
  docker compose "${args[@]}" up -d --no-deps --no-build --wait --wait-timeout 120 max-bot
  exit 1
fi
BASH
```

Compose использует существующие файлы, не выводя их содержимое. В этой установке
образ бота — `max-glpi-bot:webhook`. MariaDB и Nginx не пересоздаются.

## Одна команда диагностики

После обновления образа:

```bash
sudo docker exec -i max_bot node scripts/diagnose-webhook.mjs --watch 30
```

Команда выводит username бота и результат проверки подписки, затем проверяет
авторизованный POST напрямую и через Docker Nginx с TLS. Ожидаются
`Node callback: HTTP 200, OK` и `Nginx HTTPS → callback: HTTP 200, OK`.
Ответ сверяется с nonce пробы и ID текущего процесса: чужой HTTP 200 не считается
успехом. Затем в течение 30 секунд отправьте новый `/start` в MAX.
Пробные события игнорируются и считаются отдельно от настоящих событий MAX.
Подписка, бизнес-сессии и GLPI командой не изменяются, сообщения в MAX не отправляются.
Токен/секрет не выводятся; `.env` команда не открывает.

`--local-only --watch 0` проверяет локальную цепочку без MAX API. Код завершения
0 подтверждает локальную проверку и, без `--local-only`, совпадение подписки.
Настоящую доставку показывает отдельное число событий за окно наблюдения.
Итоги и пределы проверки — [WEBHOOK_AUDIT.md](WEBHOOK_AUDIT.md).

Новые сообщения из webhook подсчитываются отдельно: attempted/confirmed/failed.
`confirmed` требует ответа MAX с `message.body.mid`, но не подтверждает прочтение.
Выводятся последние пять из 20 завершённых настоящих событий: статус, результат,
длительность и счётчики ответов. Пробы не вытесняют историю. Фоновые уведомления,
editMessage и answerOnCallback в эти счётчики не входят. `processed` без нового
ответа возможен при раннем return; дубликат имеет отдельный `result=duplicate`.
После повторного молчания соберите `--watch 0` до перезапуска контейнера.
Сравнение с Python-ботами и порядок работы — [WEBHOOK_COMPARISON.md](WEBHOOK_COMPARISON.md).

Основной бот получает события MAX только через webhook. В нём нет запуска long polling
MAX или автоматического возврата к `/updates`. SDK-методы `bot.start()`,
`bot.api.getUpdates()`, `bot.api.raw.subscriptions.getUpdates()` и обычный raw GET
`/updates` заблокированы до сетевого запроса. Общий HTTP-клиент MAX также
отклоняет `/updates` для raw-вызовов и кодированных путей. Команды и кнопки проходят через ту же
цепочку middleware и обработчиков.

Опрос заявок GLPI и регистрационных заявок СДС — отдельные обращения к GLPI/SQL,
которые не получают события MAX и не конфликтуют с webhook. Исходящие сообщения,
уведомления, вложения и ответы на callbacks используют REST API MAX: webhook
предназначен для доставки входящих событий, а не для отправки сообщений ботом.

## Настройки

В существующей конфигурации контейнера добавьте:

```text
BOT_TRANSPORT=webhook
WEBHOOK_URL=https://botsupport.gov70.ru/max/callback/
WEBHOOK_SECRET=<отдельный-случайный-секрет>
PORT=3000
```

Замените placeholder настоящим случайным секретом: 5–256 символов `A-Z`, `a-z`, `0-9`, `_`, `-`.
Рекомендуется 32 случайных байта в hex; сгенерировать можно командой `openssl rand -hex 32`.
Сохраните значение в защищённых настройках запуска, не в репозитории и не в переписке.
Рабочие `.env` при разработке не читались и не изменялись.

Все прежние настройки `BOT_TOKEN`, БД, GLPI, importer и SMTP сохраняются.
Без `BOT_TRANSPORT` также используется `webhook`. Значение `polling` отклоняется
до запуска и сетевых запросов. Без `WEBHOOK_URL` и `WEBHOOK_SECRET` запуск прерывается.
Адрес обработчика берётся из пути `WEBHOOK_URL`:
расхождения между подпиской и HTTP-маршрутом нет. В URL нельзя задавать query, fragment или учётные данные.

## Подготовка до установки сертификата

Из каталога `bot/` установите зависимости и запустите тесты:

```bash
npm ci
DOTENV_CONFIG_PATH=/dev/null npm test
```

Тесты используют фиктивные токены и локальный HTTP; не читают рабочую `.env`,
не регистрируют настоящие подписки и не отправляют сообщений в MAX/GLPI.
Тест MariaDB выполняется только при отдельно заданном `RCAIR_TEST_DB_PORT`.
Отдельный тест использует настоящий SDK, реальные обработчики и локальную заглушку
MAX API: проверяет `/start`, текст, кнопку меню, `bot_started`, исходящее уведомление
и нулевое число запросов `/updates`. Попытки включить polling отклоняются.

Образ можно собрать заранее из `bot/`:

```bash
docker build -t max-glpi-bot:webhook .
```

Полный Docker build требует доступа к реестру образов, npm и источнику доверенных CA из Dockerfile.
Проверку TLS отключать нельзя. В текущей доработке выполнялись тесты Node.js 22;
боевой образ и обращения к рабочим MAX/GLPI отдельно не проверялись.

Для локальных регрессионных тестов сертификат не нужен: они используют HTTP-заглушки.
Регистрировать боевой webhook следует после того, как публичный HTTPS на
`botsupport.gov70.ru` доступен снаружи с доверенной цепочкой. При сбое HTTPS или
MAX API новый релиз не запускает polling вместо webhook.

## Публикация после установки сертификата

1. Публичные A/AAAA-записи должны указывать на доступный внешний адрес.
   Проверьте проброс TCP 443 и обратный маршрут до сервера бота.
   Если Nginx работает на хосте, входящий TCP 443 должен быть разрешён в `INPUT`:
   опубликованные Docker-порты могут использовать другой путь через файрвол.
2. Установите сертификат для `botsupport.gov70.ru` и полную цепочку.
   Для Docker используется [deploy/nginx.docker.conf](deploy/nginx.docker.conf).
   Шаблон [deploy/nginx.conf.example](deploy/nginx.conf.example) оставлен для Nginx
   на хосте и отката. Если TLS завершает отдельный
   корпоративный прокси, настройте такой же маршрут там, без второго публичного Nginx.
3. Сохраните существующие сети и параметры БД при обновлении контейнера бота.
   Для Nginx на хосте публикуйте Node-порт только на loopback:
   `-p 127.0.0.1:3000:3000`. При Nginx в другом контейнере используйте общую Docker-сеть
   и имя сервиса в `proxy_pass`, а не `127.0.0.1` соседнего контейнера.
4. Остановите старый экземпляр polling и запустите обновлённый контейнер с
   `BOT_TRANSPORT=webhook`, `WEBHOOK_URL` и `WEBHOOK_SECRET`. Не запускайте
   одновременно несколько экземпляров одного бота: сериализация диалогов локальна процессу.

При старте бот проверяет подписки и учётную запись, открывает listener и регистрирует
три события: `message_created`, `message_callback`, `bot_started`, с тем же секретом,
который проверяется в `X-Max-Bot-Api-Secret`.
В логе `[GLPI_TICKETS]` относится к проверке заявок GLPI. Получение событий MAX
отмечается `[MAX_WEBHOOK]`; запросов GET `/updates` основной бот не выполняет.

Существующие подписки на другие URL автоматически не удаляются: перенос такого
бота требует явного решения владельца. При совпадающем URL подписка регистрируется
повторно с актуальными событиями и секретом. При ошибке MAX/регистрации процесс
завершается с ненулевым кодом; supervisor контейнера может перезапустить его.

## Проверка после запуска

Внутри контейнера проверьте readiness:

```bash
node -e "fetch('http://127.0.0.1:3000/health').then(async r => { console.log(r.status, await r.text()); process.exitCode = r.ok ? 0 : 1; }).catch(() => { process.exitCode = 1; })"
```

Ожидается `200` и `{"ok":true,"service":"max-bot","transport":"webhook"}`.
До подтверждённой регистрации readiness отвечает `503`. Readiness подтверждает
завершение запуска, но не доказывает доставку событий из интернета.

С мобильного интернета или внешней машины:

```bash
curl --connect-timeout 10 --max-time 20 -I https://botsupport.gov70.ru/max/callback/
```

Ожидается `403` от приложенного Nginx, поскольку разрешён только POST.
Прямой GET к Node-обработчику возвращает `405`. Тайм-аут или ошибка сертификата
означают, что внешний HTTPS ещё не готов; отсутствующая обычная HTML-страница
не мешает приёму webhook.

Далее отправьте `/start` своему боту в MAX, пройдите вход и проверьте меню/кнопки,
создание тестовой заявки и уведомление GLPI. В access log Nginx должен быть
`POST /max/callback/` с `200`, а в MAX — ответ бота. Ошибка обработки даёт `500`.
Полная рабочая цепочка требует реальных сервисов и тестовой учётной записи;
локальные регрессионные тесты её не заменяют.

В журнале приложения строки `[MAX_WEBHOOK]` связывают приём и результат по номеру
`event` в пределах процесса. `stage=received` содержит тип события и флаги
распознанного `/start` и наличия пользователя. `stage=finished` показывает
`processed`, `duplicate` или `ignored`, HTTP-код и длительность; `stage=failed`
показывает ошибочный HTTP-код. Строка `received` без результата помогает заметить
долгую обработку. Это завершение middleware, а не гарантия отправленного ответа:
ожидаемое сообщение в MAX проверяется отдельно. Текст, MAX ID, callback payload,
ID сообщения и секрет в эти диагностические записи не включаются.

`stage=request` фиксирует начало callback POST до проверки секрета и тела.
`stage=rejected` с `reason=secret` означает отказ авторизации, `stopping` —
остановку приёма событий. Внутренний GET `/diagnostics` содержит счётчики и активные
запросы; публичный Nginx его не проксирует. JSON-запросы SDK и подписки ограничены
30 секундами с реальной отменой HTTP. Для `attachment.not.ready` — два повтора.

## Доставка, повторы и остановка

- Проверка секрета выполняется до чтения тела. Тело — JSON, максимум 1 МиБ;
  невалидный JSON получает `400`, другой content type — `415`, превышение лимита — `413`.
- HTTP `200` отправляется после завершения обработчика. Исключение даёт `500`,
  чтобы MAX мог повторить доставку; текст исключения и токены в ответ не включаются.
  Обработчики `/start` и `bot_started` передают ошибку транспорту, если не удалось
  отправить даже сообщение об ошибке, вместо подтверждения потерянного ответа.
- Повторные `message_created` с одним `mid` и callbacks с одним `callback_id`
  объединяются в процессе обработки и запоминаются на 10 минут (не более 10000).
  Неуспешное событие можно повторить. Это память одного процесса: после рестарта
  повторы возможны; гарантии exactly-once для GLPI нет. `bot_started` дедуплицируется
  по хешу timestamp/chat/user/payload. Последовательность обработки MAX ID сохранена.
- При SIGINT/SIGTERM приём останавливается, текущим HTTP-запросам даётся до 15 секунд,
  затем закрываются GLPI-сессия и БД. Подписка не удаляется при остановке, чтобы
  последующий запуск сохранил доставку. Периодические таймеры GLPI/очистки останавливаются.
- Переключение `BOT_TRANSPORT=polling` не поддерживается. Для аварийного отката
  используется отдельный резервный образ и его конфигурация; в данном релизе
  остаётся только входящий webhook MAX.

Долгие GLPI/importer операции могут превысить срок ожидания отправителя и вызвать
повтор webhook. Nginx не переигрывает POST на другой backend. Для нескольких
экземпляров или гарантий сохранения входящих событий потребуется отдельная
персистентная очередь и идемпотентность операций GLPI.


## Этапы ожидания и дополнительные таймауты

Диагностика выводит события MAX с запуска и активные этапы. dialog.wait — очередь
предыдущего события пользователя; db.bot.acquire/db.glpi.acquire — ожидание
соединения; db.*.execute — SQL; max.api, glpi.api, glpi.import, smtp.send —
соответствующий вызов. В ошибке фиксируется этап, без SQL/параметров/секретов.

По умолчанию DB_ACQUIRE_TIMEOUT_MS=3000, DB_QUERY_TIMEOUT_MS=10000,
SMTP_TIMEOUT_MS=10000. Дополнительные настройки для установки исправлений
не нужны. Таймаут SMTP ограничивает соединение, приветствие и простой сокета.
При таймауте SQL запись могла завершиться на сервере: автоповтора нет.


## Приём событий при повторной регистрации

Listener начинает принимать авторизованные callback сразу после открытия порта:
контроллеры, БД и botInfo подготовлены до этого. Действующая подписка может
доставить событие раньше, чем вернётся POST регистрации; оно обрабатывается
и дедуплицируется обычным образом. Readiness остаётся 503 до подтверждения
регистрации. При ошибке регистрации listener закрывается, как и ранее.
При остановке приём прекращается независимо от статуса регистрации.
