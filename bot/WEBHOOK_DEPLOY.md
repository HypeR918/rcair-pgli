# Webhook GLPI-бота MAX

Публичный адрес: **https://botsupport.gov70.ru/max/callback/**.

```text
MAX → botsupport.gov70.ru:443 → Nginx (TLS) → Node.js:3000 → существующие обработчики → GLPI
```

Webhook заменяет только long polling MAX. Опрос заявок GLPI, регистрационных заявок СДС,
уведомления, авторизация и существующие команды остаются теми же.

## Настройки

В существующей конфигурации контейнера добавьте:

```text
BOT_TRANSPORT=webhook
WEBHOOK_URL=https://botsupport.gov70.ru/max/callback/
WEBHOOK_SECRET=<отдельный-случайный-секрет>
PORT=3000
```

Замените placeholder настоящим случайным секретом: 5–256 символов `A-Z`, `a-z`, `0-9`, `_`, `-`.
Рекомендуется 32 случайных байта в hex; сгенерировать можно командой `openssl rand -hex 32`.
Сохраните значение в защищённых настройках запуска, не в репозитории и не в переписке.
Рабочие `.env` при разработке не читались и не изменялись.

Все прежние настройки `BOT_TOKEN`, БД, GLPI, importer и SMTP сохраняются.
Без `BOT_TRANSPORT` используется прежний режим `polling`, чтобы существующий запуск
не сломался до подготовки HTTPS. Адрес обработчика берётся из пути `WEBHOOK_URL`:
расхождения между подпиской и HTTP-маршрутом нет. В URL нельзя задавать query, fragment или учётные данные.

## Подготовка до установки сертификата

Из каталога `bot/` установите зависимости и запустите тесты:

```bash
npm ci
DOTENV_CONFIG_PATH=/dev/null npm test
```

Тесты используют фиктивные токены и локальный HTTP; не читают рабочую `.env`,
не регистрируют настоящие подписки и не отправляют сообщений в MAX/GLPI.
Тест MariaDB выполняется только при отдельно заданном `RCAIR_TEST_DB_PORT`.

Образ можно собрать заранее из `bot/`:

```bash
docker build -t max-glpi-bot:webhook .
```

Полный Docker build требует доступа к реестру образов, npm и источнику доверенных CA из Dockerfile.
Проверку TLS отключать нельзя. В текущей доработке выполнялись тесты Node.js 22;
боевой образ и обращения к рабочим MAX/GLPI отдельно не проверялись.

До подготовки HTTPS оставьте рабочий бот в `polling`. Для локальной разработки и
тестов сертификат не нужен. Регистрировать боевой webhook следует после того,
как публичный HTTPS на `botsupport.gov70.ru` доступен снаружи с доверенной цепочкой.

## Публикация после установки сертификата

1. Публичные A/AAAA-записи должны указывать на доступный внешний адрес.
   Проверьте проброс TCP 443 и обратный маршрут до сервера бота.
2. Установите сертификат для `botsupport.gov70.ru` и полную цепочку.
   Шаблон [deploy/nginx.conf.example](deploy/nginx.conf.example) содержит итоговый TLS-конфиг:
   замените пути сертификата/ключа перед включением. Если TLS завершает отдельный
   корпоративный прокси, настройте такой же маршрут там, без второго публичного Nginx.
3. Сохраните существующие сети и параметры БД при обновлении контейнера бота.
   Для Nginx на хосте публикуйте Node-порт только на loopback:
   `-p 127.0.0.1:3000:3000`. При Nginx в другом контейнере используйте общую Docker-сеть
   и имя сервиса в `proxy_pass`, а не `127.0.0.1` соседнего контейнера.
4. Остановите старый экземпляр polling и запустите обновлённый контейнер с
   `BOT_TRANSPORT=webhook`, `WEBHOOK_URL` и `WEBHOOK_SECRET`. Не запускайте
   одновременно несколько экземпляров одного бота: сериализация диалогов локальна процессу.

При старте бот проверяет подписки и учётную запись, открывает listener и регистрирует
три события: `message_created`, `message_callback`, `bot_started`, с тем же секретом,
который проверяется в `X-Max-Bot-Api-Secret`.

Существующие подписки на другие URL автоматически не удаляются: перенос такого
бота требует явного решения владельца. При совпадающем URL подписка регистрируется
повторно с актуальными событиями и секретом. При ошибке MAX/регистрации процесс
завершается с ненулевым кодом; supervisor контейнера может перезапустить его.

## Проверка после запуска

Внутри контейнера проверьте readiness:

```bash
node -e "fetch('http://127.0.0.1:3000/health').then(async r => { console.log(r.status, await r.text()); process.exitCode = r.ok ? 0 : 1; }).catch(() => { process.exitCode = 1; })"
```

Ожидается `200` и `{"ok":true,"service":"max-bot","transport":"webhook"}`.
До подтверждённой регистрации readiness отвечает `503`. Readiness подтверждает
завершение запуска, но не доказывает доставку событий из интернета.

С мобильного интернета или внешней машины:

```bash
curl --connect-timeout 10 --max-time 20 -I https://botsupport.gov70.ru/max/callback/
```

Ожидается `403` от приложенного Nginx, поскольку разрешён только POST.
Прямой GET к Node-обработчику возвращает `405`. Тайм-аут или ошибка сертификата
означают, что внешний HTTPS ещё не готов; отсутствующая обычная HTML-страница
не мешает приёму webhook.

Далее отправьте `/start` своему боту в MAX, пройдите вход и проверьте меню/кнопки,
создание тестовой заявки и уведомление GLPI. В access log Nginx должен быть
`POST /max/callback/` с `200`, а в MAX — ответ бота. Ошибка обработки даёт `500`.
Полная рабочая цепочка требует реальных сервисов и тестовой учётной записи;
локальные регрессионные тесты её не заменяют.

В журнале приложения строки `[MAX_WEBHOOK]` связывают приём и результат по номеру
`event` в пределах процесса. `stage=received` содержит тип события и флаги
распознанного `/start` и наличия пользователя. `stage=finished` показывает
`processed`, `duplicate` или `ignored`, HTTP-код и длительность; `stage=failed`
показывает ошибочный HTTP-код. Строка `received` без результата помогает заметить
долгую обработку. Это завершение middleware, а не гарантия отправленного ответа:
ожидаемое сообщение в MAX проверяется отдельно. Текст, MAX ID, callback payload,
ID сообщения и секрет в эти диагностические записи не включаются.

## Доставка, повторы и остановка

- Проверка секрета выполняется до чтения тела. Тело — JSON, максимум 1 МиБ;
  невалидный JSON получает `400`, другой content type — `415`, превышение лимита — `413`.
- HTTP `200` отправляется после завершения обработчика. Исключение даёт `500`,
  чтобы MAX мог повторить доставку; текст исключения и токены в ответ не включаются.
  Обработчики `/start` и `bot_started` передают ошибку транспорту, если не удалось
  отправить даже сообщение об ошибке, вместо подтверждения потерянного ответа.
- Повторные `message_created` с одним `mid` и callbacks с одним `callback_id`
  объединяются в процессе обработки и запоминаются на 10 минут (не более 10000).
  Неуспешное событие можно повторить. Это память одного процесса: после рестарта
  повторы возможны; гарантии exactly-once для GLPI нет. `bot_started` без отдельного
  ID события не дедуплицируется. Механизм последовательной обработки MAX ID сохранён.
- При SIGINT/SIGTERM приём останавливается, текущим HTTP-запросам даётся до 15 секунд,
  затем закрываются GLPI-сессия и БД. Подписка не удаляется при остановке, чтобы
  последующий запуск сохранил доставку. Периодические таймеры GLPI/очистки останавливаются.
- Возврат на polling: остановите webhook-экземпляр, явно удалите его подписку в MAX
  и запустите `BOT_TRANSPORT=polling`. С активной подпиской запуск polling отклоняется.

Долгие GLPI/importer операции могут превысить срок ожидания отправителя и вызвать
повтор webhook. Nginx не переигрывает POST на другой backend. Для нескольких
экземпляров или гарантий сохранения входящих событий потребуется отдельная
персистентная очередь и идемпотентность операций GLPI.
